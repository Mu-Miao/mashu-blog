## 一帧十六个字节，最后四个是"不可能出现的数"

板子能收命令、能算速度之后，剩下的问题是：**怎么看见它内部正在发生什么**。打文本行当然可以，但我想看曲线。

上位机软件（VOFA+）支持一种很朴素的协议叫 JustFloat：不做任何转义、不带长度字段，就是**按顺序摆几个 4 字节单精度浮点（小端），最后接一个固定的四字节帧尾**。我发三路——目标值、实际速度、PWM 输出，于是：

| 字节 | 内容 |
|---|---|
| 0–3 | 通道 1：`target` 的 float |
| 4–7 | 通道 2：`speed` 的 float |
| 8–11 | 通道 3：`pwm` 的 float |
| 12–15 | 帧尾 `00 00 80 7F` |

最有意思的是那四个字节。`00 00 80 7F` 按小端读回来是 `0x7F800000`，**这正好是 IEEE 754 单精度正无穷的位模式**。也就是说，协议用"数据里正常情况下不可能出现的数"当标点符号，告诉上位机"一帧到此为止"。漏了它的症状很明确：解析错位，三条波形全成毛刺。

另一件让我挺得意的事是——**这段代码里没有 `printf`**：

```c
static void vofa_justfloat3(float a, float b, float c)
{
  float f[3] = {a, b, c};
  static const uint8_t tail[4] = {0x00, 0x00, 0x80, 0x7F};
  HAL_UART_Transmit(&huart1, (uint8_t *)f, sizeof(f), 10);
  HAL_UART_Transmit(&huart1, (uint8_t *)tail, 4, 10);
}
```

浮点在内存里本来就是 4 字节小端，把 `float[3]` 当原始字节整块发出去，就已经是一帧合法的 JustFloat。既省掉格式化开销，又顺手绕开了 newlib-nano 打 `%f` 还要额外链接参数那个坑。**同一个需求，绕开一条坑比填平它便宜。**

## 上波形之前，我先自己数了一遍字节

我不会直接相信上位机的图。我的顺序是反过来：**先证明"发出去的东西"是对的，再证明"画出来的东西"是对的。**

第一步是抓一帧原始字节，数够不够 16 个、末尾四个是不是 `00 00 80 7F`、通道顺序有没有搞反。第二步是分帧逻辑单独验：发长短不同的命令（一个字符、五个字符、带不带换行），看每次算出来的 `len` 是不是跟着变——这才能证明"帧长 = 缓冲区总长 − DMA 剩余计数"那条公式在跑，而不是碰巧第一帧对。

顺便还有一个小细节：上位机发过来的是 ASCII 数字，我用 `atoi` 转，而它遇到 `\r` 会自动停下来，所以带不带换行都不用我先裁剪字符串。**这种"正好不用处理"的细节，值得在写完时回头看一眼是谁在替你省事。**

主循环里的处理顺序我也调过一次：中断里只拷数据、举一个 `volatile` 的旗子，解析放到主循环做。旗子要**先放低再处理**，否则处理期间进来的下一帧会被吞掉。

## 波特率决定我敢采多快

这条纯算术，但它让我避免了"为什么曲线卡顿"这种无头绪问题。115200 下一个字节约 86.8 µs，一帧 16 字节就是：

- 一帧发送耗时：16 × 86.8 µs ≈ **1.39 ms**（115200 的位时间是 8.68 µs，8N1 一帧是 10 位）
- 我主循环是 `HAL_Delay(10)` + 1.39 ms + 少量执行 ⇒ 实际周期略大于 10 ms，也就是 **约 88 Hz 的采样率**
- 流量：16 字节 × 88 次 ≈ **1.4 KB/s**，而 115200 扣掉起止位后的净吞吐约 **11.5 KB/s**，余量还有八倍左右

看到这几个数我就知道两件事：10 ms 这个采样间隔不是波特率逼我的，是我的 `Delay` 定的；而如果想把采样提到 1 ms，串口就会变成瓶颈——那时候要动的不是"把 Delay 改小"这一行，而是整条链路的吞吐。

**能把"我觉得卡"翻译成"哪一段占了多少毫秒"，调试就从猜变成了查账。** 这也是我越来越喜欢把每一层的数字写下来的原因：板子不会跟你吵架，它只是安静地按算术运行。

—— 麻薯ta爸
