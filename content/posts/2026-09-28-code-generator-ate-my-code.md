## 一行蒸发的 `#include`

我用 CubeMX 配好芯片和外设，让它生成工程，然后在 `main.c` 第 23 行附近加了 `#include <stdio.h>`——位置很正常，编译通过，运行正常。

第二天我改了一个波特率，重新 GENERATE CODE，回来发现**编译不过了**：`implicit declaration of function 'printf'`。我那行 `#include` 不见了。

这不是 bug，是它的工作方式：**生成器每次都会重写它自己维护的那几段**，包括那段 `/* Includes --- */` 列表。它没有"我不动别人的代码"这种义务，因为它压根认为那块地是它的。规矩只有一条：

> 自己写的东西，一律放进 `/* USER CODE BEGIN xxx */` 和 `/* USER CODE END xxx */` 之间。

这条我实测验证过：把波特率和时钟改了重生成一遍，我写在保护区里的回显补丁**五行一字未动**。反过来，放在外面的任何一行都可能哪天早上消失。

而且这台机器的编译器是 Arm GNU **14**，它把"隐式声明 printf"直接判成错误，不是警告。老版本的 GCC 只会抱怨一句然后照样链接，所以你要是从旧教程里抄代码，很可能连"我踩了这个坑"都没意识到，只觉得项目莫名其妙开始报错了。

## 保护区的名字就是它的用途

这些区名看着像乱码，其实是有分工的，我现在的习惯是这样填：

| 区名 | 我放什么 |
|---|---|
| `Includes` | 头文件 |
| `PV` | 全局变量 |
| `0` | 函数定义 |
| `PFP` | 只放函数声明 |
| `2` | `while(1)` 之前的初始化、启动外设 |
| `WHILE` | 主循环体 |
| `USART1_IRQn 0` / `1` | 中断里 HAL 调用**之前**和**之后**的两道缝 |

最后一行那两个数字不是编号，是**顺序**：同一个函数里被 HAL 自己的代码隔开的两个空档。我后来踩的一个坑，全部关键在于代码要贴进哪一道缝——贴错了不会报错，只会行为诡异。

## 保存 ≠ 生成，而配置文件才是事实源

另一个坑更安静。`.ioc` 文件记录的是图形界面里的配置，我改完按了 Ctrl+S，以为万事大吉，继续写代码、烧录、然后困惑于"我明明改了"。

**保存 `.ioc` 和重新生成代码是两个动作。** 判断自己有没有漏点，只要比一下文件时间：`.ioc` 是 21:12，而 `main.c` 还停在 21:10，那中间那十几分钟我做的配置全都只活在界面里。

顺带一条更好用的判据：**CubeMX 只把"你改过的参数"写进 `.ioc`**。所以某个外设下面一行 `TIMx.` 都没有，意思就是它全是默认值，不是"我记得我设过"。这比截图和记忆都可信——我第一次靠这条发现我以为自己改过的输入过滤器，其实一直是 0。

## 串口没输出，因为 `fputc` 不在这条路上

我照着一份写得很权威的说明做了 printf 重定向：

```c
int _write(int file, char *ptr, int len)
{
  HAL_UART_Transmit(&huart1, (uint8_t *)ptr, len, HAL_MAX_DELAY);
  return len;      /* 这个返回值不能省：负数会被 newlib 当成写失败，printf 一个字都不出 */
}
```

而我一开始写的版本是 `int fputc(int ch, FILE *f)`——**编译通过、烧录成功、串口一个字符都不吐**。因为 `fputc` 那条路是 ARMCC/Keil 家的口径；换成 Arm GNU Toolchain + newlib，`printf` 底层走的是 `_write`，而工程里那个 `_write` 是个 weak 桩函数，逐字符调用一个从未定义的 `__io_putchar`。所以我的实现被链接器温柔地忽略了，一个字节都没有。

同类"数字显示不出来"还有一个：`%f` 在这套配置里是空的或者乱码，因为链接只带了 `--specs=nano.specs --specs=nosys.specs`，newlib-nano 默认不链浮点打印，要么加 `-u _printf_float`，要么老老实实全用 `%d` 把浮点自己乘 100 当定点。顺便，换行要写 `\r\n`，只给 `\n` 的话上位机会把几十行内容挤成一行。

这三件事有个共同点：**代码没有错，是"你在对另一个编译器说话"。**
